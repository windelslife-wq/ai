# Architecture

Dedicated Node 22+ Express process, no runtime link to CI3/PHP, no shared database tables, no frontend framework. All new tables use `fp_` prefix in a dedicated MySQL/MariaDB database. `public/` serves browser assets; `server.js` owns all APIs and session authorization; `server/providers/apiFootball.js` is the only upstream adapter; `server/jobs/` owns scheduled sync, never generation. `server/generation.js` can only be invoked by authenticated CSRF-protected admin POST. MySQL unique `fp_generation.day` and `fp_tickets.day` prevent duplicate daily generation/tickets. Publication requires a separate admin POST.

## Flow

Cron syncs fixtures, Over 1.5 odds, completed team form, verified fixture results. Each cron obtains a MySQL named lock and writes a sync log. Generation checks upstream status and retrieves fresh odds per candidate fixture; an empty current provider market cannot be replaced with a stale stored market. It rejects invalid fixture/status/source/timestamp/price, insufficient history, low data quality/confidence or high risk, records per-fixture rejection reasons, searches bounded combinations, rechecks locked rows, and writes immutable ticket selections, snapshots and a qualified generation report in one transaction. Failure records FAILED, not a public ticket. If no qualifying combination, the attempt records NO_QUALIFYING_TICKET and a report; no ticket row is inserted.

A publisher approves a DRAFT independently. Unpublishing hides it from public reads; settlement operates on all persisted selections and does not mutate snapshot prices or original combined odds. Results sync writes real provider statuses and goals, then idempotently updates pending selections/tickets in a transaction. PST stays postponed and is reevaluated until a real final/cancelled state; CANC becomes VOID; AET/PEN require recorded full-time regulation goals.

## Model and limits

`empirical-form-2` is a transparent **baseline, not trained AI**. Requires >=8 completed games per team and >=3 venue-specific games each, plus fresh form sync and recently completed games. Smoothed Over 1.5 rate `(hits+2)/(n+4)` is blended 20% home last ten, 20% away last ten, 15% home last five, 15% away last five, 15% home-at-home and 15% away-away. Scoring/conceding rates and average total goals are reported from real team form; scoring consistency adds a 0–10-point risk penalty. Quality measures sample completeness and recentness; confidence is an evidence score, NOT calibrated success probability. Risk is `0.6*(100-100*p)+0.4*(100-quality)+round(10*(1-mean scoring consistency))` rounded. Bookmaker implied probability is deliberately not independent model evidence; `1/price` is stored as a separate bookmaker-implied probability and displayed independently; it is not a calibration factor. No H2H, injuries, standings or league goals are used without a verified sample; this is a limitation, not invented data. Marginal probabilities are not empirically calibrated; accumulator multiplication assumes independence, with separately labeled heuristic team/competition restrictions. Do not use this model to claim real accuracy until validated out of sample.

Optimizer limits: top 24 candidates, 50,000 evaluated branches, configurable maximum 2–12 legs, shared-team rule and per-competition cap. Truncation is reported. Exact finite-decimal multiplication uses BigInt; original prices and product are stored as strings so trailing precision is retained. UI rounds only for display. Combination utility is joint baseline probability multiplied by `(1-average risk/100)`, **not** highest odds. A search cap means it may reject when an unexamined combination exists; it never invents one.

## UTC and persistence

Connection timezone Z; DATETIME(3) is UTC by convention; public API emits `Z`. `fp_odds` is append-only and unique by fixture/bookmaker/market/observed-at/payload-hash. Ticket selections snapshot fixture names, bookmaker, price, source hash, model version and scores. `fp_results` is current verified provider state. Migrations are checksum-checked; DDL is not atomic in MySQL, so back up first and retry a failed idempotent first migration only after manual schema inspection.
